# Agent 性能验证

## 2026-11-12 复查

基线是拉取并确认 `origin/main` 最新后、已包含本次 RDP 重连采集的工作区；优化前后均使用 Go 1.26.11、`CGO_ENABLED=0`、`-trimpath -tags=nethttpomithttp2 -ldflags='-s -w'`。不使用压缩壳，也不移除 TLS 或持久化功能。

| 平台 | 优化前字节数 | 数据库优化后字节数 |
| --- | ---: | ---: |
| Linux amd64 | 6,574,242 | 6,578,338 |
| Linux arm64 | 6,095,010 | 6,095,010 |
| Windows amd64 | 7,003,136 | 7,007,744 |
| Windows arm64 | 6,338,560 | 6,341,632 |

本轮优先降低数据库开销，体积基本持平，最多增加约 4.5 KiB。arm64 验证交叉编译，未测实机运行占用。

### 本地数据库

Agent 使用 bbolt 持久队列，不是主控的 SQLite/MySQL/PostgreSQL。保留同步落盘以及事件和游标的原子事务。

- 附加日志源使用最多 64 项的游标缓存，缓存淘汰后从数据库恢复；只有提交成功才更新缓存，重新注册会清空缓存。
- 无事件且游标不变时不启动写事务，避免等待不完整日志行时反复写入相同游标；正常无变化文件原本就会提前返回。
- 读取上传批次时按最多 100 条预分配，减少切片扩容和复制。

Windows / i5-12600KF、`-cpu=2 -count=3` 的微基准：

| 操作 | 优化前 | 优化后 |
| --- | --- | --- |
| 附加源游标读取 | 1.57–1.68 µs；936 B / 14 次分配 | 23–25 ns；0 分配 |
| 提交不变的附加源游标 | 1.78–1.96 ms；约 8.5 KB / 66 次分配 | 50–53 ns；0 分配、无磁盘写入 |
| 读取 100 条上传批次 | 88,384 B / 1,216 次分配 | 61,664 B / 1,209 次分配 |

批次读取分配减少约 30%，耗时存在噪声，未据此宣称吞吐提升。连续四轮填满并确认删除 10,000 条样本事件，数据库均为 8,388,608 字节，证明该负载下空闲页会复用。bbolt 文件保持历史高水位，不会随删除立即缩小；本轮未添加有额外停机、重写成本的自动压缩。8 MiB 不是所有事件大小下的硬上限。

### 进程占用

`scripts/checks/measure-agent.py` 使用隔离配置、本地 HTTP ACK 服务、1 秒上报间隔，预热 5 秒后每 250 ms 采样 15 秒。突发为每秒 100 条 SSH 登录和 400 条约 2 KiB 无关日志；每组共 1,500 条登录，均成功收到。Linux 在 WSL Ubuntu amd64 中运行，数据文件位于 Linux 临时目录。只测父进程，不代表系统服务、Windows 事件通道、journalctl 或长期离线积压。

| 平台 / 场景 | 优化前平均 RSS | 优化后平均 RSS | 优化后峰值 |
| --- | ---: | ---: | ---: |
| Windows 空闲文件 | 15.56 MiB | 15.54 MiB | 15.62 MiB |
| Windows 500 行/秒 | 18.30 MiB | 18.16 MiB | 18.79 MiB |
| Linux 空闲文件 | 10.90 MiB | 11.43 MiB | 11.43 MiB |
| Linux 500 行/秒 | 11.86 MiB | 11.97 MiB | 12.26 MiB |

内存整体持平；这些短时差值不足以认定改善或回退。Linux CPU 采样约占单核 0.07–0.46%；Windows 此短窗口计时未捕获可分辨 CPU 增量，不能解释为无 CPU 开销。文件采集未直接覆盖附加源缓存的最佳收益场景。

验证包括 Windows/Linux agent 回归、原生 Windows 事件句柄释放、300 次传输重连（goroutine 3→3）、数据库重启恢复、失败提交不推进缓存、身份重置、缓存上限和页复用。Linux race 检查受当前 WSL 缺少 GCC 限制，未完成。

复现数据库基准：`go test ./internal/agent -run '^$' -bench 'SpoolSecondary|SpoolBatch' -benchmem -count=3 -cpu=2`。运行占用采样：`python scripts/checks/measure-agent.py <agent 可执行文件>`。

## Windows 内存

两个版本同时连接本地 HTTP 确认服务，上报间隔 5 秒。每 250 毫秒采样，总共 60 次；均值使用预热约 5 秒后的 40 次采样。数据为 Agent 父进程工作集，未计入旧版本短暂启动的 `wevtutil.exe` 子进程。短时测试受系统缓存影响，不代表长期生产峰值或硬性上限。

| 场景 | 优化前平均工作集 | 优化后平均工作集 |
| --- | ---: | ---: |
| 空闲文件采集 | 18.06 MiB | 17.48 MiB |
| 空闲 Windows 事件采集 | 17.94 MiB | 18.19 MiB |
| 文件突发，每秒 500 行 | 19.71 MiB | 18.19 MiB |

突发场景每秒包含 100 条有效 SSH 登录和 400 条约 2 KB 的无关日志；工作集峰值从 20.23 MiB 降至 18.37 MiB。空闲 Windows 事件采集父进程内存基本持平，但不再创建采集子进程。

## 实现与验证

- Windows 使用 `EvtQuery` / `EvtNext` / `EvtRender`，逐条解析并关闭句柄；固定查询线程，限制单事件和单批渲染大小。
- 复用文件读取、UTF-16 解码缓冲区；只为匹配事件构建持久化事件 ID，避免无关日志的字符串与散列开销。
- VNC 时间解析基准从每行 7–8 次分配降至 0 次，样本耗时约改善 10–30 倍。这是解析微基准，不是整个 Agent 吞吐提升。
- 默认 Go 内存软目标 32 MiB、最多 2 个 Go 执行线程，尊重显式环境变量。该目标不限制进程总工作集；队列映射和系统资源等不计入 Go 软目标。
- `go test ./...` 通过，包括事件读取与旧工具内容对比、取消、句柄稳定性、采集及队列回归；四个平台构建通过。Linux/arm64 仅验证交叉编译，本轮未测其运行时内存。

可复现解析基准：`go test ./internal/agent -run '^$' -bench 'VNC' -benchmem`。生产部署后仍应结合事件量、离线积压和真实 VNC 软件日志观察长期占用。
